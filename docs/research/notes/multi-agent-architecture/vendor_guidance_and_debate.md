# Vendor guidance and the practitioner debate on production multi-agent LLM architecture (state as of 30 September 2026)

Dating conventions used below: **[OLDER]** = published 2024 or first half of 2025; each such item says whether a later source superseded it. Quotes are as returned by page fetches (a small summarising model extracted them), so treat wording as near-verbatim and check the primary page before quoting in a final report.

## 1. What do Anthropic's engineering posts say, and what did 2026 add?

### Takeaway
Anthropic's line is consistent from Dec 2024 to 2026: use the simplest thing that works (single call, then workflow, then agent, then multi-agent), and adopt multi-agent only for context protection, parallelisable breadth, or specialisation. The 2026 additions are (a) explicit cost multiples and a "context-centric" decomposition rule, (b) evidence that a separate, sceptically tuned evaluator is the most reliable quality lever, (c) a warning that every harness component is an assumption that goes stale as models improve, and (d) productised forms of these patterns (Managed Agents outcomes/multiagent, advisor tool, dynamic workflows).

### Cited Findings

**Foundational (older, still cited by everyone)**
- **[OLDER, Dec 19 2024; not superseded, still the reference taxonomy]** "Building effective agents", Erik S. (Schluntz) and Barry Zhang. Defines workflows as "systems where LLMs and tools are orchestrated through predefined code paths" and agents as "systems where LLMs dynamically direct their own processes and tool usage". Recommends "finding the simplest solution possible, and only increasing complexity when needed". — [Anthropic](https://www.anthropic.com/engineering/building-effective-agents)
- Same post, five workflow patterns and when to use them: prompt chaining (task "can be easily and cleanly decomposed into fixed subtasks"); routing ("distinct categories that are better handled separately, and where classification can be handled accurately", including routing to differently sized models); parallelisation (sectioning and voting, "when multiple perspectives or attempts are needed for higher confidence results"); orchestrator-workers ("complex tasks where you can't predict the subtasks needed"); evaluator-optimizer ("particularly effective when we have clear evaluation criteria, and when iterative refinement provides measurable value"). — [Anthropic](https://www.anthropic.com/engineering/building-effective-agents)
- Same post: frameworks "often create extra layers of abstraction that can obscure the underlying prompts and responses, making them harder to debug"; three principles are simplicity, transparency (show planning steps), and a carefully documented and tested agent-computer interface. — [Anthropic](https://www.anthropic.com/engineering/building-effective-agents)
- **[OLDER, Jun 13 2025; numbers still the most-quoted, partly refined by the Jan 2026 post below]** "How we built our multi-agent research system", Jeremy Hadfield, Barry Zhang, Kenneth Lien, Florian Scholz, Jeremy Fox, Daniel Ford. Opus 4 lead + Sonnet 4 subagents "outperformed single-agent Claude Opus 4 by 90.2% on our internal research eval". — [Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)
- Same post, cost: "agents typically use about 4× more tokens than chat interactions, and multi-agent systems use about 15× more tokens than chats"; "token usage by itself explains 80% of the variance" on BrowseComp, with tool calls and model choice as the other factors. — [Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)
- Same post, fit: good for "valuable tasks that involve heavy parallelization, information that exceeds single context windows, and interfacing with numerous complex tools"; poor fit where agents must share context or have many inter-dependencies (most coding). — [Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)
- Same post, delegation and effort scaling: "Each subagent needs an objective, an output format, guidance on the tools and sources to use, and clear task boundaries"; "Simple fact-finding requires just 1 agent with 3-10 tool calls, direct comparisons might need 2-4 subagents with 10-15 calls each, and complex research might use more than 10 subagents". — [Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)
- Same post, context passing: "Subagents call tools to store their work in external systems, then pass lightweight references back to the coordinator"; parallel tool calling "cut research time by up to 90% for complex queries"; synchronous execution means "the lead agent can't steer subagents, subagents can't coordinate, and the entire system can be blocked while waiting for a single subagent". Evals: start with "about 20 queries representing real usage patterns"; a single LLM-judge call scoring 0.0-1.0 was most consistent. — [Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)

**Context, tools, skills, MCP (Sep-Nov 2025)**
- "Writing effective tools for agents — with agents" (Sep 11 2025, Ken Aizawa et al.): "More tools don't always lead to better outcomes"; build "a few thoughtful tools targeting specific high-impact workflows"; return "only high signal information"; paginate/filter/truncate (Claude Code caps tool responses at 25,000 tokens by default); tool descriptions are "one of the most effective methods for improving tools"; develop tools against evals. — [Anthropic](https://www.anthropic.com/engineering/writing-tools-for-agents)
- "Effective context engineering for AI agents" (Sep 29 2025, Prithvi Rajasekaran, Ethan Dixon, Carly Ryan, Jeremy Hadfield): context rot — "As the number of tokens in the context window increases, the model's ability to accurately recall information from that context decreases". Subagents should each return "only a condensed, distilled summary of its work (often 1,000-2,000 tokens)". Three techniques and their fit: compaction (long back-and-forth), structured note-taking (iterative work with milestones), sub-agent architectures (complex research/analysis with parallel exploration). Just-in-time retrieval via "lightweight identifiers (file paths, stored queries, web links, etc.)". — [Anthropic](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- "Equipping agents for the real world with Agent Skills" (Oct 16 2025, Barry Zhang, Keith Lazuka, Mahesh Murag): skills are "organized folders of instructions, scripts, and resources that agents can discover and load dynamically"; three-level progressive disclosure (name/description in system prompt, then SKILL.md, then bundled files); "sorting a list via token generation is far more expensive than simply running a sorting algorithm", code gives "deterministic reliability that only code can provide". — [Anthropic](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)
- "Code execution with MCP: Building more efficient agents" (Nov 4 2025, Adam Jones, Conor Kelly): loading tool definitions on demand cut one example from 150,000 to 2,000 tokens (98.7%); filter in the execution environment so "The agent sees five rows instead of 10,000"; intermediate results passing through the model twice can cost ~50,000 extra tokens; agents can "write intermediate results to files, enabling them to resume work and track progress". — [Anthropic](https://www.anthropic.com/engineering/code-execution-with-mcp)
- "Effective harnesses for long-running agents" (Nov 26 2025, Justin Young): initializer agent + incremental coding agent; state carried across context windows by a feature-list file with `passes` flags, a progress file and git commits; one feature at a time "turned out to be critical"; explicitly left open that "it's still unclear whether a single, general-purpose coding agent performs best across contexts, or if better performance can be achieved through a multi-agent architecture". — [Anthropic](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)

**2026 updates**
- "Building multi-agent systems: When and how to use them" (Jan 23 2026, Cara Phillips with Paul Chen, Andy Schumeister, Brad Abrams, Theo Chu; Claude blog). Three cases where multi-agent wins: context protection, parallelisation, specialisation. Multi-agent systems typically consume "3 to 10 times more tokens than single-agent approaches for equivalent tasks". Decompose by context, not by problem type: "Dividing by context boundaries means an agent handling a feature should also handle its tests". Avoid splitting sequential phases (plan/implement/test) across agents ("telephone game": "each handoff loses context"). Signs you have outgrown one agent: routinely hitting context limits, 15-20+ tools, genuinely independent parallel subtasks. — [Claude blog](https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them)
- Same post on verifiers: a verification subagent is a recommended pattern, but its failure mode is "early victory" — "the verifier runs one or two tests, observes them pass, and declares success"; mitigate with explicit, mandatory completeness instructions. — [Claude blog](https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them)
- "Building a C compiler with a team of parallel Claudes" (Feb 5 2026, Nicholas Carlini): 16 agents, nearly 2,000 Claude Code sessions, two weeks, just under $20,000, 2B input / 140M output tokens, 100,000-line compiler. No orchestrator: agents claimed tasks via lock files in `current_tasks/` and git ("If two agents try to claim the same task, git's synchronization forces the second agent to pick a different one"). Specialised roles included a de-duplicator, a performance agent, a design critic and a documenter. "It's important that the task verifier is nearly perfect, otherwise Claude will solve the wrong problem." — [Anthropic](https://www.anthropic.com/engineering/building-c-compiler)
- "Harness design for long-running application development" (Mar 24 2026, Prithvi Rajasekaran): planner/generator/evaluator harness "taking inspiration from Generative Adversarial Networks". Self-evaluation is unreliable: "agents tend to respond by confidently praising the work—even when, to a human observer, the quality is obviously mediocre". "Separating the agent doing the work from the agent judging it proves to be a strong lever", and "Tuning a standalone evaluator to be skeptical turns out to be far more tractable than making a generator critical of its own work". Evaluator calibrated with few-shot examples and score breakdowns. — [Anthropic](https://www.anthropic.com/engineering/harness-design-long-running-apps)
- Same post, cost and communication: solo run 20 min / $9 versus full harness 6 h / $200 ("over 20x more expensive, but the difference in output quality was immediately apparent"). "Communication was handled via files: one agent would write a file, another agent would read it". Context resets give "a clean slate, at the cost of the handoff artifact having enough state for the next agent". — [Anthropic](https://www.anthropic.com/engineering/harness-design-long-running-apps)
- Same post, simplification: "Every component in a harness encodes an assumption about what the model can't do on its own, and those assumptions are worth stress testing... they can quickly go stale as models improve." With Opus 4.6 the sprint decomposition and per-sprint evaluation were removed in favour of a single QA pass at the end. — [Anthropic](https://www.anthropic.com/engineering/harness-design-long-running-apps)
- "Scaling Managed Agents: Decoupling the brain from the hands" (Apr 8 2026, Lance Martin, Gabe Cemaj, Michael Cohen): harness separated from sandbox; the session log is an external, interrogable context object; example of a stale assumption — Sonnet 4.5 "would wrap up tasks prematurely as it sensed its context limit approaching" but on Opus 4.5 "the behavior was gone"; be "opinionated about the interfaces around Claude" rather than specific harness logic. — [Anthropic](https://www.anthropic.com/engineering/managed-agents)
- "The advisor strategy: Give agents an intelligence boost" (Apr 9 2026, Claude blog): a cheap executor (Sonnet/Haiku) runs the task end-to-end and consults Opus as an advisor with no tools and no user-facing output; presented as inverting orchestrator-subagent (small model drives, escalates when needed). Reported: Sonnet + Opus advisor +2.7 points on SWE-bench Multilingual over Sonnet alone with 11.9% lower cost per task; Haiku + Opus advisor 41.2% vs 19.7% solo on BrowseComp. — [Claude blog](https://claude.com/blog/the-advisor-strategy). Note: third-party summaries describe the same figures as "SWE-bench Verified" and "cheaper than Opus alone", which conflicts with the primary post — [builder.io summary via search](https://www.builder.io/blog/the-claude-advisor-pattern); prefer the primary.
- "New in Claude Managed Agents: dreaming, outcomes, and multiagent orchestration" (May 19 2026 per page fetch; a secondary outlet dates its coverage May 7 2026 — date conflict unresolved): outcomes = rubric + a separate grader in an independent context window; "up to 10-point" task-success gain, +8.4% docx and +10.1% pptx on internal benchmarks. Multiagent: a lead agent delegates to specialists each with "its own model, prompt, and tools", working "in parallel on a shared filesystem", with full tracing. Dreaming: scheduled review of sessions and memory stores to curate memory. — [Claude blog](https://claude.com/blog/new-in-claude-managed-agents); date conflict: [9to5Mac listing](https://9to5mac.com/2026/05/07/anthropic-updates-claude-managed-agents-with-three-new-features/)
- Claude Agent SDK docs, "Subagents in the SDK" (undated living doc, fetched 30 Sep 2026): four benefits — context isolation, parallelisation, specialised instructions, tool restrictions. A non-fork subagent starts fresh: "The only content you pass from parent to subagent is the Agent tool's prompt string, so include any file paths, error messages, or decisions the subagent needs directly in that prompt". It does not receive the parent's history, tool results or system prompt; "only its final message returns to the parent". Per-agent `model`, `tools`, `effort`, `maxTurns`, `skills`, `mcpServers`. — [Claude Code docs](https://code.claude.com/docs/en/agent-sdk/subagents)
- Same doc, limits: subagents can nest (default depth 3, `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`), default 20 concurrent, and `max_budget_usd` caps spend across subagents. "Claude Opus 5 delegates to subagents more readily than earlier models", so the doc recommends setting those limits and a delegation instruction. — [Claude Code docs](https://code.claude.com/docs/en/agent-sdk/subagents)
- Claude Code docs, "Orchestrate subagents at scale with dynamic workflows" (undated living doc): distinguishes who holds the plan — with subagents/skills/agent teams "Claude is the orchestrator: it decides turn by turn"; a workflow "moves the plan into code", keeping loop, branching and intermediate results in script variables so "Claude's context holds only the final answer". Workflows can codify "a repeatable quality pattern", e.g. "independent agents adversarially review each other's findings before they're reported". Warns a run "can use meaningfully more tokens". — [Claude Code docs](https://code.claude.com/docs/en/workflows)

### Inferences
- Anthropic's position did not reverse between 2024 and 2026; it became more quantified and more conditional. The Jan 2026 "3-10x" figure is measured against single-agent runs on equivalent tasks, whereas the Jun 2025 "15x" is against chat, so the two are not in conflict and should not be conflated.
- For the FPL project: the design already matches Anthropic's recommended shape (orchestrator + isolated specialists, cheap model for scouting, deterministic tools for numerics, file-based hand-offs). The guidance most likely to change the design is (1) decompose by context, not by role — fixtures/transfers/chips analysts share a lot of context and may be candidates for merging; (2) a sceptic is best implemented as a separately prompted, calibrated evaluator with explicit criteria rather than a free-form arguer; (3) a weekly fixed cadence with known steps fits "workflow in code" more than turn-by-turn LLM orchestration.
- The advisor strategy is a published alternative to "large Manager orchestrating cheap workers": cheap executor, large model consulted only at hard decisions.

## 2. What do OpenAI, Google and Microsoft publish on multi-agent design?

### Takeaway
All three vendors say the same first thing as Anthropic — start with one agent and add agents only for a concrete reason — and then offer a pattern catalogue. The main taxonomic split is "manager keeps control and calls specialists as tools" versus "handoff transfers control"; all three also distinguish LLM-driven orchestration from orchestration in code, and all flag critic/review loops and swarm/group-chat as the costliest patterns.

### Cited Findings

**OpenAI**
- OpenAI developer guide "Orchestration and handoffs" (undated living doc): "Start with one agent whenever you can. Add specialists only when they materially improve capability isolation, policy isolation, prompt clarity, or trace legibility." Handoffs when "a specialist should take over the conversation for that branch of the work"; agents-as-tools when "the main agent should stay responsible for the final answer and call specialists as helpers", e.g. when "the manager should synthesize the final answer" or "the specialist is doing a bounded task like summarization or classification". Handoffs "can also carry structured metadata or filtered history". — [OpenAI developers](https://developers.openai.com/api/docs/guides/agents/orchestration)
- OpenAI Agents SDK docs "Agent orchestration" (undated living doc): two modes. Orchestrating via LLM suits open-ended tasks; tactics: "Invest in good prompts", "Monitor your app and iterate on it", "Allow the agent to introspect and improve", prefer "specialized agents that excel in one task", "Invest in evals". Orchestrating via code is "more deterministic and predictable" on "speed, cost and performance"; patterns: structured outputs for classification, chaining, an evaluator loop ("In each iteration of a `while` loop, run the task agent to produce an output, then run an evaluator agent"), and parallelism via `asyncio.gather`. — [OpenAI Agents SDK](https://openai.github.io/openai-agents-python/multi_agent/)
- Simon Willison reports OpenAI Codex subagents reached general availability on March 17 2026, with default "explorer", "worker" and "default" subagents and custom agents defined as TOML files with their own instructions and models — i.e. OpenAI's coding product converged on the Claude Code subagent shape. — [Simon Willison](https://simonwillison.net/2026/Mar/16/codex-subagents/)

**Google**
- "Developer's guide to multi-agent patterns in ADK" (Dec 16 2025, Shubham Saboo, Google Developers Blog): eight patterns — Sequential Pipeline, Coordinator/Dispatcher, Parallel Fan-Out/Gather, Hierarchical Decomposition, Generator and Critic, Iterative Refinement, Human-in-the-Loop, Composite. Generator-critic: the critic reviews "against specific, hard-coded criteria or logical checks", wrapped in a `LoopAgent` with an exit condition. Context passing: "session.state is your whiteboard"; use `output_key` so the next agent "knows exactly where to pick up the work"; in parallel runs "make sure each agent writes its data to a unique key" to avoid race conditions. "Start simple: Do not build a nested loop system on day one." Human-in-the-loop for "high-stakes actions". — [Google Developers Blog](https://developers.googleblog.com/developers-guide-to-multi-agent-patterns-in-adk/)
- "Choose a design pattern for your agentic AI system" (Google Cloud Architecture Center, last reviewed 2026-05-28 UTC): twelve patterns (single-agent, sequential, parallel, loop, review and critique, iterative refinement, coordinator, hierarchical task decomposition, swarm, ReAct, human-in-the-loop, custom logic). "If you're early in your agent development, we recommend that you start with a single agent." Review-and-critique adds "significant latency and operational expenses"; swarm is "the most complex and costly multi-agent pattern". "If your workload is predictable or highly structured, or if it can be executed with a single call to an AI model, it can be more cost effective to explore non-agentic solutions." — [Google Cloud](https://docs.cloud.google.com/architecture/choose-design-pattern-agentic-ai-system)
- A2A protocol: announced by Google Apr 9 2025, donated to the Linux Foundation Jun 2025; at its one-year mark (Apr 9 2026) the project reported 150+ supporting organisations. A2A is positioned as agent-to-agent communication across organisational boundaries, complementary to MCP (agent-to-tool). — [Linux Foundation press release](https://www.linuxfoundation.org/press/a2a-protocol-surpasses-150-organizations-lands-in-major-cloud-platforms-and-sees-enterprise-production-use-in-first-year); [A2A project: A2A and MCP](https://a2a-protocol.org/latest/topics/a2a-and-mcp/)

**Microsoft**
- "AI Agent Orchestration Patterns" (Azure Architecture Center; page metadata ms.date 2026-02-12, updated 2026-09-21): "Use the lowest level of complexity that reliably meets your requirements." Three levels: direct model call, single agent with tools, multiagent orchestration. Multi-agent is justified by cross-domain problems, "distinct security boundaries for each agent", and parallel specialisation. Five patterns: sequential, concurrent, group chat, handoff, magentic. — [Microsoft Learn](https://learn.microsoft.com/en-us/azure/architecture/ai-ml/guide/ai-agent-design-patterns)
- Same page, critic loops: maker-checker is a group-chat sub-pattern where a checker "evaluates the result against defined criteria" and returns specific feedback; "also known as evaluator-optimizer, generator-verifier, critic loops, or reflection loops". "Consider limiting group chat orchestration to three or fewer agents." — [Microsoft Learn](https://learn.microsoft.com/en-us/azure/architecture/ai-ml/guide/ai-agent-design-patterns)
- Same page, context and cost: "decide what context the next agent requires to be effective" — full raw context in some cases, a compacted summary in others; monitor accumulated context and compact between agents. "Validate agent output before you pass it to the next agent. Low-confidence, malformed, or off-topic responses can cascade through a pipeline." "Assign each agent a model that matches the complexity of its task." Use deterministic routing when routing is rule-based. Listed anti-patterns include "using a complex pattern when basic sequential or concurrent orchestration would suffice". — [Microsoft Learn](https://learn.microsoft.com/en-us/azure/architecture/ai-ml/guide/ai-agent-design-patterns)

### Inferences
- The vendor catalogues are near-isomorphic: Anthropic orchestrator-workers = OpenAI agents-as-tools/manager = Google coordinator/hierarchical = Microsoft magentic/concurrent; Anthropic evaluator-optimizer = Google generator-critic/review-and-critique = Microsoft maker-checker.
- The FPL Manager pattern is "agents as tools" in OpenAI's terms (manager owns the final answer). No vendor recommends handoffs for that shape; handoffs are for conversational ownership transfer, which a weekly batch agent does not need.
- A2A is about cross-organisation interoperability and is not relevant to a single-process personal project; MCP for the xP model and MILP optimiser is the matching layer.

## 3. What is the sceptical view, and where has the debate landed by 2026?

### Takeaway
The 2025 "don't build multi-agents" versus "multi-agent works" dispute has largely converged: the leading sceptic (Cognition) now ships multi-agent systems, under the rule that writes stay single-threaded and extra agents contribute intelligence (review, advice, read-only exploration) rather than parallel actions. Residual disagreement is about how much to decompose and whether the orchestration should live in the model or in code.

### Cited Findings
- **[OLDER, Jun 12 2025; explicitly refined by the same author in Apr 2026]** "Don't Build Multi-Agents", Walden Yan, Cognition. Two principles: "Share context, and share full agent traces, not just individual messages" and "Actions carry implicit decisions, and conflicting decisions carry bad results". Flappy Bird example: parallel subagents produce a mismatched background and bird. Notes Claude Code then ran subagents non-parallel and only for answering questions, not writing code. Conclusion: in multi-agent collaboration "decision-making ends up being too dispersed". — [Cognition](https://cognition.com/blog/dont-build-multi-agents)
- **[OLDER, Jun 16 2025; still accurate as the reconciliation]** "How and when to build multi-agent systems", Harrison Chase, LangChain. Argues the Cognition and Anthropic posts agree: "context engineering is crucial" and "multi-agent systems that primarily 'read' are easier than those that 'write'"; Anthropic kept report writing in a single agent. Production needs durable execution, observability and evals starting from "~20 datapoints". — [LangChain](https://www.langchain.com/blog/how-and-when-to-build-multi-agent-systems)
- "Choosing the Right Multi-Agent Architecture" (Jan 14 2026, Sydney Runkle, LangChain): "Many agentic tasks are best handled by a single agent with well-designed tools. You should start here". Four patterns — subagents, skills, handoffs, router. Published comparison: one-shot request 4 model calls for subagents vs 3 for the others; repeat request 4 vs 2 (skills, handoffs) vs 3 (router); multi-domain query ~9K tokens for subagents and router vs ~15K for skills and ~14K+ for handoffs. Subagents add latency but isolate context. — [LangChain](https://www.langchain.com/blog/choosing-the-right-multi-agent-architecture)
- "Multi-Agents: What's Actually Working" (Apr 22 2026, Walden Yan, Cognition). Core rule: "multi-agent systems work best today when writes stay single-threaded and the additional agents contribute intelligence rather than actions." Says models have become "way more naturally 'agentic'". — [Cognition](https://cognition.com/blog/multi-agents-working)
- Same post, review agents: counterintuitively "the coding and review agents do not share any context beforehand"; a clean-context reviewer avoids context rot and reasons backward from the implementation. Devin Review "catches an average of 2 bugs per PR, of which roughly 58% are severe". — [Cognition](https://cognition.com/blog/multi-agents-working)
- Same post, "smart friend" pattern: a weaker primary model consults a stronger one. Worked across frontier models but failed with SWE-1.5 as the primary: "The gap between it and Sonnet 4.5 was too wide in exactly the places that mattered for this setup: knowing when to escalate, knowing what to ask." — [Cognition](https://cognition.com/blog/multi-agents-working)
- Same post: "the unstructured-swarm approach, arbitrary networks of agents negotiating with each other, is mostly a distraction"; the working large-scale shape is manager-splits / children-execute / manager-synthesises. Open problems are all "communication problems": when a weaker model should escalate, how a child surfaces discoveries that affect siblings, how to transfer context without overwhelming the receiver. — [Cognition](https://cognition.com/blog/multi-agents-working)
- Simon Willison, "Subagents" chapter of "Agentic Engineering Patterns" (chapter added Mar 17 2026 per his site's listing; page itself shows no date): subagents are "a simple but effective way to handle larger tasks without burning through too much of the coding agent's valuable top-level context"; parallel subagents can use "faster and cheaper models such as Claude Haiku". Caution: "While it can be tempting to go overboard breaking up tasks across dozens of different specialist subagents, it's important to remember that the main value of subagents is in preserving that valuable root context." — [Simon Willison](https://simonwillison.net/guides/agentic-engineering-patterns/subagents/)
- **[OLDER, Jun 8 2024; not superseded as engineering advice, but predates current models]** "What We've Learned From A Year of Building with LLMs", Eugene Yan, Bryan Bischof, Charles Frye, Hamel Husain, Jason Liu, Shreya Shankar: "the likelihood that an agent completes a multi-step task successfully decreases exponentially as the number of steps increases"; prefer having "agent systems produce deterministic plans which are then executed in a structured, reproducible way"; "small prompts that do one thing, and only one thing, well"; "The model isn't the product, the system around it is." — [applied-llms.org](https://applied-llms.org/)
- **[OLDER, Jan 7 2025; not superseded]** Chip Huyen, "Agents": "If the model's accuracy is 95% per step, over 10 steps, the accuracy will drop to 60%"; "Planning should be decoupled from execution. You ask the agent to first generate a plan, and only after this plan is validated is it executed"; reflection costs latency and tokens; "most agents are multi-agent" if each component counts as an agent. — [Chip Huyen](https://huyenchip.com/2025/01/07/agents.html)
- Hamel Husain and Shreya Shankar, evals FAQ (page reports published Sep 18 2026, modified Sep 21 2026 — this may be a re-dated living page): "Error analysis is the most important activity in evals"; review "the first upstream failure" in a trace because "errors tend to compound"; "Binary evaluations force clearer thinking and more consistent labeling" versus Likert scales. — [hamel.dev](https://hamel.dev/blog/posts/evals-faq/)

### Inferences
- Where the debate landed: orchestrator + context-isolated specialists returning summaries, read-heavy fan-out, single writer, and a clean-context reviewer is now common ground between Anthropic, Cognition, LangChain, OpenAI, Google and Microsoft. Swarms/peer negotiation are the pattern nobody serious defends for production.
- Where experts still differ: (a) Cognition's original "share full traces" versus the Anthropic/Claude Code default of fresh subagent context plus a brief — reconciled in practice by "isolate for read/review, share for anything that writes"; (b) LLM-as-orchestrator versus plan-in-code (applied-llms authors, Chip Huyen, OpenAI's code-orchestration mode and Claude Code workflows all lean to code for predictable tasks); (c) big-model-orchestrates-small versus small-model-executes-and-escalates (Anthropic advisor, Cognition smart friend).
- For the FPL agent, the sceptic's read-only, advisory role is exactly the class Cognition now endorses; Cognition's finding that reviewers do better without the author's context supports giving the sceptic only the proposed move and the data, not the Manager's reasoning. The Cognition warning about weak primaries not knowing when to escalate applies to a cheap-model news scout deciding what is worth flagging.

## 4. What evidence exists on whether debate/critic/sceptic agents and multi-agent setups improve results, and at what token cost?

### Takeaway
Evidence favours an independent evaluator with explicit criteria and a clean context, and favours centralised orchestration on parallelisable tasks; it does not favour free-form multi-agent debate, which repeatedly fails to beat cheaper single-agent baselines, and multi-agent setups degrade sequential reasoning. Token cost multiples reported by vendors range from roughly 2-3x (debate versus self-correction) through 3-10x (multi-agent versus single agent) to 15x versus chat and 20x+ for a full generator/evaluator harness.

### Cited Findings

**Multi-agent versus single agent**
- "Towards a Science of Scaling Agent Systems" (arXiv 2512.08296; Google Research blog Jan 28 2026, Yubin Kim and Xin Liu): 180 agent configurations. Centralised coordination improved a parallelisable financial-reasoning task by about 81% (blog says 80.9%; abstract summaries say 80.8%); on sequential reasoning/planning tasks every multi-agent variant degraded performance by 39-70%. Independent agents amplified errors up to 17.2x versus 4.4x under centralised coordination. Coordination overhead grows disproportionately for tool-heavy tasks (16+ tools). Predictive model R²=0.513, picks the best architecture for 87% of unseen configurations. — [Google Research blog](https://research.google/blog/towards-a-science-of-scaling-agent-systems-when-and-why-agent-systems-work/); [arXiv](https://arxiv.org/abs/2512.08296)
- **[OLDER, v1 Mar 17 2025, v3 Oct 26 2025]** "Why Do Multi-Agent LLM Systems Fail?" (Cemri, Pan, Yang, Agrawal, Chopra, Tiwari, Keutzer, Parameswaran, Klein, Ramchandran, Zaharia, Gonzalez, Stoica): MAST taxonomy of 14 failure modes in 3 categories from 1,600+ annotated traces across 7 frameworks (kappa 0.88). Shares: system design issues 43.8% (step repetition 15.7%, unaware of stopping conditions 12.4%, disobey task specification 11.8%); inter-agent misalignment 32.25% (reasoning-action mismatch 13.2%, task derailment 7.4%, fail to ask clarification 6.8%); task verification 23.5% (incorrect verification 9.1%, no/incomplete verification 8.2%, premature termination 6.2%). Failure rates of 41% to 86.7% across the frameworks studied. — [arXiv abstract](https://arxiv.org/abs/2503.13657); [arXiv v3 full text](https://arxiv.org/html/2503.13657v3)
- Same paper: "many MAS failures arise from the challenges in organizational design and agent coordination rather than the limitations of individual agents"; targeted fixes on ChatDev gave +9.4% (workflow/role change) and +15.6% (adding high-level task verification), yet completion stayed low, so "more substantial improvements are needed". Caveat: models studied were GPT-4, Claude 3, Qwen2.5, CodeLlama — older than 2026 frontier models. — [arXiv v3](https://arxiv.org/html/2503.13657v3)
- Anthropic's own positive result: multi-agent research beat single-agent Opus 4 by 90.2% on an internal (breadth-first research) eval, at about 15x chat tokens. — [Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)

**Debate, critics, sceptics**
- **[OLDER, Feb 12 2025, v3 Jun 21 2025]** "Stop Overvaluing Multi-Agent Debate -- We Must Rethink Evaluation and Embrace Model Heterogeneity" (Zhang, Cui, Chen, Wang, Zhang, Wang, Wu, Hu): 5 debate methods, 9 benchmarks, 4 models; debate methods "often fail to outperform simple single-agent baselines such as Chain-of-Thought and Self-Consistency, even when consuming significantly more inference-time computation". Model heterogeneity is "a universal antidote" that consistently improves debate. — [arXiv](https://arxiv.org/abs/2502.08788)
- "The Cost of Consensus: Isolated Self-Correction Prevails Over Unguided Homogeneous Multi-Agent Debate" (Apr 29 2026, Blaž Bertalanič, Carolina Fortuna): debate used "2.1-3.4× more tokens (up to 28,631 tokens per problem) than self-correction for equal or lower accuracy". Mechanisms: sycophantic conformity (agents adopting majority answers up to 85.5%), peer rationales undermining correct reasoning (70% vulnerability), voting discarding correct answers (32.3-point oracle gap). Caveat: tested only on 7-8B open models (Qwen2.5-7B, Llama-3.1-8B, Ministral-3-8B). — [arXiv](https://arxiv.org/abs/2605.00914)
- Earlier evidence in the same direction: "Large Language Models Cannot Self-Correct Reasoning Yet" (arXiv 2310.01798, 2023) is reported as finding multi-agent debate underperforms self-consistency at an equal number of responses; and "When and Why Does Multi-Agent Debate Fail and Does It Really Underperform?" (arXiv 2510.20963) surveys the accumulating negative evidence. Both seen only as search summaries, not fetched. — [arXiv 2310.01798](https://arxiv.org/pdf/2310.01798); [arXiv 2510.20963](https://arxiv.org/html/2510.20963)
- Positive evidence for a separated evaluator (vendor-reported, not peer-reviewed): Anthropic's harness post ("Separating the agent doing the work from the agent judging it proves to be a strong lever"; tuned-sceptical evaluator; 20x+ cost) — [Anthropic](https://www.anthropic.com/engineering/harness-design-long-running-apps); Managed Agents outcomes (separate grader, up to 10 points task success) — [Claude blog](https://claude.com/blog/new-in-claude-managed-agents); Cognition's clean-context reviewer (2 bugs per PR, ~58% severe) — [Cognition](https://cognition.com/blog/multi-agents-working).
- Verifier failure modes: "early victory" (verifier declares success after one or two checks) — [Claude blog](https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them); MAST's verification category is 23.5% of observed failures — [arXiv v3](https://arxiv.org/html/2503.13657v3).

**Token cost summary**
- ~4x (single agent vs chat) and ~15x (multi-agent vs chat) — [Anthropic, Jun 2025](https://www.anthropic.com/engineering/multi-agent-research-system)
- 3-10x (multi-agent vs single agent, equivalent task) — [Claude blog, Jan 2026](https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them)
- 20x+ ($9 vs $200; planner/generator/evaluator harness vs solo) — [Anthropic, Mar 2026](https://www.anthropic.com/engineering/harness-design-long-running-apps)
- 2.1-3.4x (debate vs isolated self-correction) — [arXiv, Apr 2026](https://arxiv.org/abs/2605.00914)
- Review-and-critique requires at least one extra model call and adds "significant latency and operational expenses" — [Google Cloud](https://docs.cloud.google.com/architecture/choose-design-pattern-agentic-ai-system)

### Inferences
- The literature separates two things often lumped together as "critic": (1) symmetric debate among similar agents converging by discussion or vote — weak evidence, conformity failure modes; (2) an asymmetric evaluator with a clean context, explicit pass/fail criteria and ideally a different model — consistently reported as useful. A "sceptic that argues against the proposed move" sits between the two; the evidence suggests pushing it toward (2): criteria-driven, blind to the Manager's rationale, different model from the proposer, and unable to be talked round by the proposer.
- FPL gameweek planning is closer to sequential, interdependent reasoning (transfers, chips and fixtures interact under one budget) than to breadth-first research, which is the task class where the Google study found multi-agent degradation. The read-only fan-out part (news scouting) is the parallelisable part where gains are expected.
- For a once-a-week run, a 3-10x token multiple is small in absolute terms, so cost is a weaker argument against multi-agent here than error amplification and debuggability.

### Gaps
- No controlled, peer-reviewed study of a devil's-advocate/sceptic agent on frontier 2026 models was found; vendor results are internal benchmarks without published methodology.
- The debate-negative papers mostly use older or small models and QA/maths benchmarks; transfer to decision tasks under uncertainty (such as FPL) is untested.
- The per-benchmark breakdown in the Google scaling paper was not read in the full text; only the blog and abstract-level figures are cited.
- No published evidence specifically on heterogeneous-model sceptics (e.g. a different vendor's model as critic) beyond the 2025 heterogeneity recommendation.

## 5. What concrete rules of thumb recur across sources?

### Takeaway
Roughly a dozen rules recur across at least two independent sources; the most robust are: climb the complexity ladder only when forced, split by context rather than by role, keep a single writer, brief subagents fully because they start cold, pass references to files rather than payloads, put predictable control flow and all numeric work in code, and keep the judge separate from the worker.

### Cited Findings
- **Start with the lowest complexity that works.** "only increasing complexity when needed" — [Anthropic](https://www.anthropic.com/engineering/building-effective-agents); "Start with one agent whenever you can" — [OpenAI](https://developers.openai.com/api/docs/guides/agents/orchestration); "Use the lowest level of complexity that reliably meets your requirements" — [Microsoft](https://learn.microsoft.com/en-us/azure/architecture/ai-ml/guide/ai-agent-design-patterns); "start with a single agent" — [Google Cloud](https://docs.cloud.google.com/architecture/choose-design-pattern-agentic-ai-system); "You should start here" — [LangChain](https://www.langchain.com/blog/choosing-the-right-multi-agent-architecture).
- **Add agents only for a named reason.** Context protection, parallelisation, specialisation — [Claude blog](https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them); "capability isolation, policy isolation, prompt clarity, or trace legibility" — [OpenAI](https://developers.openai.com/api/docs/guides/agents/orchestration); security boundaries and cross-domain work — [Microsoft](https://learn.microsoft.com/en-us/azure/architecture/ai-ml/guide/ai-agent-design-patterns).
- **Decompose by context boundary, not by job title; do not split sequential phases.** — [Claude blog](https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them); main value of subagents is "preserving that valuable root context" — [Simon Willison](https://simonwillison.net/guides/agentic-engineering-patterns/subagents/).
- **Single-writer principle; extra agents read, review or advise.** — [Cognition, Apr 2026](https://cognition.com/blog/multi-agents-working); read-heavy is easier than write-heavy — [LangChain](https://www.langchain.com/blog/how-and-when-to-build-multi-agent-systems); in shared state, one unique key per parallel agent — [Google ADK guide](https://developers.googleblog.com/developers-guide-to-multi-agent-patterns-in-adk/).
- **Subagents start cold: the brief is the whole context.** Objective, output format, tools/sources guidance, task boundaries — [Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system); "include any file paths, error messages, or decisions the subagent needs directly in that prompt" — [Claude Agent SDK docs](https://code.claude.com/docs/en/agent-sdk/subagents).
- **Return distilled summaries; store bulk output externally and pass references.** 1,000-2,000-token summaries — [Anthropic](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents); "pass lightweight references back to the coordinator" — [Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system); agents communicate via files — [Anthropic](https://www.anthropic.com/engineering/harness-design-long-running-apps); `output_key` into shared state — [Google ADK guide](https://developers.googleblog.com/developers-guide-to-multi-agent-patterns-in-adk/); compact between agents — [Microsoft](https://learn.microsoft.com/en-us/azure/architecture/ai-ml/guide/ai-agent-design-patterns).
- **Scale effort to task difficulty with explicit budgets and caps.** 1 agent/3-10 calls up to 10+ subagents — [Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system); depth, concurrency and spend caps (`max_budget_usd`) — [Claude Agent SDK docs](https://code.claude.com/docs/en/agent-sdk/subagents).
- **Match model to role.** "Assign each agent a model that matches the complexity of its task" — [Microsoft](https://learn.microsoft.com/en-us/azure/architecture/ai-ml/guide/ai-agent-design-patterns); cheaper models for parallel subagents — [Simon Willison](https://simonwillison.net/guides/agentic-engineering-patterns/subagents/); but a weak primary may not know when to escalate — [Cognition](https://cognition.com/blog/multi-agents-working).
- **Separate the judge from the worker; give it criteria and a clean context.** — [Anthropic](https://www.anthropic.com/engineering/harness-design-long-running-apps); [Cognition](https://cognition.com/blog/multi-agents-working); critic checks "specific, hard-coded criteria" — [Google ADK guide](https://developers.googleblog.com/developers-guide-to-multi-agent-patterns-in-adk/); evaluator-optimizer needs "clear evaluation criteria" — [Anthropic](https://www.anthropic.com/engineering/building-effective-agents). Guard against "early victory" — [Claude blog](https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them).
- **Put predictable control flow in code and numeric/deterministic work in tools.** Code orchestration is "more deterministic and predictable" — [OpenAI Agents SDK](https://openai.github.io/openai-agents-python/multi_agent/); a workflow "moves the plan into code" — [Claude Code docs](https://code.claude.com/docs/en/workflows); deterministic plans executed reproducibly — [applied-llms.org](https://applied-llms.org/); code gives "deterministic reliability" — [Anthropic skills post](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills); filter data in the execution environment — [Anthropic MCP post](https://www.anthropic.com/engineering/code-execution-with-mcp).
- **Few, well-described, token-efficient tools.** — [Anthropic](https://www.anthropic.com/engineering/writing-tools-for-agents); 15-20+ tools is a sign to split — [Claude blog](https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them); overhead grows at 16+ tools — [Google Research](https://research.google/blog/towards-a-science-of-scaling-agent-systems-when-and-why-agent-systems-work/).
- **Validate between steps and plan before acting.** "Validate agent output before you pass it to the next agent" — [Microsoft](https://learn.microsoft.com/en-us/azure/architecture/ai-ml/guide/ai-agent-design-patterns); validate the plan before execution — [Chip Huyen](https://huyenchip.com/2025/01/07/agents.html); centralised orchestration contains error amplification (4.4x vs 17.2x) — [Google Research](https://research.google/blog/towards-a-science-of-scaling-agent-systems-when-and-why-agent-systems-work/).
- **Human approval for high-stakes actions.** — [Google ADK guide](https://developers.googleblog.com/developers-guide-to-multi-agent-patterns-in-adk/); HITL as reviewers in maker-checker loops — [Microsoft](https://learn.microsoft.com/en-us/azure/architecture/ai-ml/guide/ai-agent-design-patterns).
- **File-based memory across runs.** Progress file, feature list and git — [Anthropic](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents); structured note-taking — [Anthropic](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents).
- **Trace everything; start evals small; read traces; binary judgments.** ~20 cases — [Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system), [LangChain](https://www.langchain.com/blog/how-and-when-to-build-multi-agent-systems); error analysis first, first upstream failure, binary pass/fail — [Hamel Husain and Shreya Shankar](https://hamel.dev/blog/posts/evals-faq/); near-perfect verifier — [Anthropic](https://www.anthropic.com/engineering/building-c-compiler).
- **Re-test the harness when the model changes; remove scaffolding that is no longer needed.** — [Anthropic, Mar 2026](https://www.anthropic.com/engineering/harness-design-long-running-apps); [Anthropic, Apr 2026](https://www.anthropic.com/engineering/managed-agents).
- **Avoid swarms and large group chats.** "mostly a distraction" — [Cognition](https://cognition.com/blog/multi-agents-working); "most complex and costly" — [Google Cloud](https://docs.cloud.google.com/architecture/choose-design-pattern-agentic-ai-system); three or fewer agents in group chat — [Microsoft](https://learn.microsoft.com/en-us/azure/architecture/ai-ml/guide/ai-agent-design-patterns).

### Inferences
- Mapped to the FPL design: deterministic xP/MILP tools behind MCP, file-based memory, approval gates and tracing are each directly endorsed by multiple sources. The elements most exposed to the published criticism are (1) three separate mid-model analysts whose subject matter is interdependent (context-boundary rule, sequential-task degradation), (2) a sceptic implemented as debate rather than as a criteria-driven, clean-context evaluator, and (3) LLM-driven orchestration of a weekly sequence that is largely known in advance (plan-in-code rule).
- A single-writer reading of the design: only the Manager (via the optimiser and an approval gate) should commit transfers, captaincy or chips; analysts and the sceptic should be read-only, which the SDK's per-subagent `tools` restriction can enforce.
- "Re-test the harness when the model changes" implies the multi-agent decomposition should be validated against a single-agent baseline on past gameweeks rather than assumed; no source offers a way to know in advance which wins for a given task.

### Gaps
- No source gives a quantitative threshold for when to merge specialists; the 15-20 tool and "three or fewer agents" figures are heuristics stated without supporting data.
- None of the sources addresses low-frequency, batch decision agents (weekly cadence) specifically; the guidance is drawn from coding, research and customer-service settings.
- Rules here are drawn from the sources actually fetched; OpenAI's "A practical guide to building agents" and the Karpathy/swyx positions are not represented (see gaps in sections 2 and 3).
